# Feature Archive, Kakeibo, and Mathematical Correctness Audit

Date: 2026-09-07  
Scope: Active Features 005 and 010 through 023, current Domain/Application
financial behavior, and PostgreSQL expense integrity.

## Executive Verdict

Features 010 through 015 and 018 through 023 are complete bounded slices and
have moved to `docs/features/archive`. Feature 005 was already archived; its
byte-identical active duplicate was removed.

Features 016 and 017 remain active. Feature 016 formats USD-denominated ledger
values as EUR, CAD, GBP, or AUD without conversion. A currency symbol asserts
denomination, so that behavior is financially misleading even though the
numeric decimal is unchanged. Feature 017's generic `¤` mode is honest, but its
named-currency restore path depends on Feature 016 and remains blocked with it.

## Kakeibo Alignment

The current product is aligned with the expense-observation foundation of
Kakeibo:

- the calendar makes spending review date-centered;
- expenses use the four initial reflective classifications Necessities,
  Optional, Culture, and Unexpected;
- account ownership and authoritative transaction history preserve context;
- daily and month-to-date totals derive from persisted records rather than
  Client-side copies.

It does not yet implement a complete Kakeibo cycle. Income, intended savings,
spending plans, classification totals, intention-versus-actual comparison, and
end-of-period reflection are explicitly deferred or absent. These are roadmap
gaps, not defects in the archived slices. After correcting currency semantics,
new core features should prioritize receive, plan, save, spend, and reflect
outcomes before further workspace presentation work.

## Mathematical And Integrity Findings

### Corrected

1. Expense amounts now reject values above
   `9,999,999,999,999,999.99`, the positive maximum of the original
   PostgreSQL `numeric(18,2)` contract.
2. Monthly summaries now query an inclusive first/last date and iterate by day
   number. December 9999 no longer overflows while trying to construct the
   following month.
3. Account-history criteria now reject undefined expense classifications at
   the Application boundary, independently of HTTP parsing.
4. PostgreSQL expense storage now uses exact unrestricted `numeric` with check
   constraints for positivity, the supported maximum, at most two decimal
   places, and the four supported classifications. This prevents PostgreSQL
   from silently rounding a direct `1.001` write to `1.00`.

Ordinary sums remain exact because .NET `decimal` and PostgreSQL `numeric` are
base-10 decimal types and accepted transaction values have at most two decimal
places. No floating-point arithmetic is used for ledger amounts.

### Remaining Risks

- Daily and month-to-date aggregation has no explicit overflow response if an
  impractically large number of maximum-value rows exceeds .NET `decimal`.
- Account normalized-name consistency is generated by the Domain and protected
  by a unique database index, but PostgreSQL does not independently prove that
  `normalized_name` was derived from `name`.
- The new PostgreSQL constraints compiled and their focused test was
  discovered, but execution skipped because
  `HOUSEHOLDLEDGER_TEST_POSTGRES_CONNECTION_STRING` was not configured.

## Recommended Next Outcome

Use Feature 024 to make denomination truthful. The smallest safe direction is
to retain USD and generic `¤` presentation while removing unsupported named
currency relabeling; real alternative currencies require explicit ledger
denomination and conversion rules. Subsequent features should establish
monthly income, intended savings, a classified spending plan, actual-versus-
plan review, and a calm end-of-period reflection flow.
